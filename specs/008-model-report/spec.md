# Feature Specification: Model report and model card data

**Feature Branch**: `008-model-report`

**Created**: 2026-11-09

**Status**: First version, after the three models were approved (V2-52, V2-55, V2-58)

**Input**: User description: "Feature 008 · Model report and model card (roadmap 008, issue #79):
one command regenerates, from the recorded runs of the approved models, a report on the three
forecasts (the data, the methods, the walk-forward results per test year against the baselines,
calibration, the chosen levels and why, the hypotheses) and the test-year hit rates the app's model
card shows. It replaces Gemini's `sentinel report`, which writes numbers typed in by hand."

## Context

Three forecasts are approved and in `main`: dilution (007, LightGBM, V2-52), the results-day move
(006, LightGBM, V2-55) and volatility (005, LightGBM, V2-58). Each was built in its notebook, which
logs its runs in MLflow (`data/mlflow.db`; experiments `007-dilution`, `006-results-move`,
`005-volatility`): one run per level and test year with the measures, a run for the hypothesis
checks and one for the frozen model.

The project needs one written account of them, for the hand-in report (019, 18 November) and for
the app's model card, which tells a user how good each forecast has been. The rules: reports are
**generated by commands, never edited by hand** (constitution), they regenerate from a clone plus
the data, and written findings quote **aggregates only** (Tiingo terms).

Gemini's `sentinel report` (`src/sentinel/models/report.py`) draws its tables and charts from
numbers typed into the code: an invented calibration curve, coverage figures and feature
importances, several contradicting MLflow (audit, 4 Nov); its output is committed as
`docs/model_report.md` with three figures. The app's model card page is typed in as well.

What the recorded runs hold today is not enough for a report: the per-level, per-year measures are
there, but not the tables a reader needs (the fold counts, the choice with its yearly gaps, the
bands with their hit rates, the calibration or range coverage, the hypothesis verdicts, the frozen
model's setting). Those exist only as notebook outputs, which are never committed.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One command writes the model report from the recorded runs (Priority: P1)

The researcher runs one command and gets the model report: for each of the three questions, the
question and its answer as pre-registered, the data, the method, every level's results per test
year against the baselines, the choice and why, the honesty of the chances or the range, the bands
with what happened in them, the hypothesis verdicts, the decisions that shaped the model (with
their caveats), and the frozen model. Every number comes from the recorded runs; none is typed in.

**Why this priority**: the hand-in report and every claim about the models rest on it; a report
with typed-in numbers cannot be trusted or regenerated.

**Independent Test**: run the command on the recorded runs; open the report; every number in its
tables equals the value recorded in MLflow.

**Acceptance Scenarios**:

1. **Given** the three models' recorded runs, **When** the command runs, **Then** it writes the
   report and its figures, and says where.
2. **Given** a question whose runs are missing or incomplete, **When** the command runs, **Then**
   it stops with a message naming the question and the notebook to run, and writes nothing.
3. **Given** the same recorded runs, **When** the command runs twice, **Then** the two outputs are
   identical.
4. **Given** the report, **When** it is read, **Then** each question's section names the recorded
   run it came from (experiment, commit, export date, data hash).

---

### User Story 2 - The model card's numbers come from the same runs (Priority: P2)

The app's model card shows, for each forecast, how good it has been: its chosen level against the
baselines per test year, and for each band what really happened (the real dilution rate, the real
shares of moves above 5%, 10%, 20%, the median real volatility and the range's coverage). The
command writes these numbers as a data file the app reads, from the same runs as the report.

**Why this priority**: the product shows every forecast with its past hit rate (D47, D62); a typed-in
model card can drift from the models.

**Independent Test**: open the data file; each band's hit rate equals the report's band table.

**Acceptance Scenarios**:

1. **Given** the command's output, **When** the model card data is read, **Then** it holds, per
   question, the chosen level, the deciding measure per test year for it and the baselines, and the
   band table with hit rates per test year and overall.
2. **Given** a change in the recorded runs (a re-run of a notebook), **When** the command runs
   again, **Then** the report and the model card data change together.

---

### User Story 3 - The holdout results go in as they came out (Priority: P3)

After the guarded holdout test (010, 16 November) has run, the same command adds each model's
holdout results to the report and the model card data exactly as recorded by the guarded command,
with its date; before that, the report says the test has not run yet.

**Why this priority**: the holdout test is the one honest check of the chosen models; its results
must appear unedited, next to the test years.

**Independent Test**: with a recorded holdout run (synthetic in the tests), the report's holdout
section shows its numbers; without one, it says "not run yet".

**Acceptance Scenarios**:

1. **Given** no holdout run, **When** the command runs, **Then** each question's holdout section
   says the test has not run yet.
2. **Given** a recorded holdout run, **When** the command runs, **Then** the holdout section shows
   its numbers and the date, unedited.

### Edge Cases

- **Trial runs** (`SENTINEL_TRIAL=1`) and runs of older notebook versions (Gemini's experiments, the
  first 005 run before V2-57) are in the same store: only the runs of the approved notebooks at
  their recorded commit are read, never a mix.
- **A notebook re-run** writes a new set of runs: the command reads the newest complete set and
  names it.
- **Aggregates only**: the report never shows one company's prices, returns or answers.
- **Missing MLflow store** (a fresh clone): the command says which notebooks to run first.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: One command MUST write the model report (Markdown with its figures) and the model card
  data from the recorded runs; no number in them may be typed into the code.
- **FR-002**: Each model notebook (`notebooks/005-…`, `006-…`, `007-…`) MUST record, in one run of
  its experiment, the tables the report needs: the data summary, the fold counts, every level's
  measures per test year, the choice with its yearly gaps and standard errors, the bands with their
  hit rates per test year, the calibration or range coverage, the hypothesis verdicts and the
  frozen model's setting and cutoffs. The notebooks MUST be re-run once to record them and MUST give
  the same numbers as their approved runs.
- **FR-003**: The command MUST read, for each question, the newest complete set of runs recorded by
  the approved notebook (not a trial, not an older version), and name it in the report (experiment,
  run, git commit, export date, data hash).
- **FR-004**: Each question's section MUST hold: the question and its answer (from
  `config/risk_params.yaml`), the data (rows, companies, years, base rate or spread), the method
  (the four levels, the walk-forward years, the `Dated` cutoffs, the choice rule V2-50), the results
  table (level × test year, deciding measure and the others), the choice and why (and the textbook
  rule's choice for reference), the decisions that shaped the model and their caveats (V2-36,
  V2-53, V2-54, V2-57), the chances' calibration or the range's coverage, the bands with their
  outcomes, the hypothesis verdicts, the frozen model, and the holdout section.
- **FR-005**: The report MUST quote aggregates only.
- **FR-006**: The command MUST be deterministic: the same recorded runs give byte-identical outputs.
- **FR-007**: The model card data MUST hold, per question, the chosen level, the deciding measure per
  test year for it and its baselines, and the band table with its hit rates (D47); the app (011)
  reads it.
- **FR-008**: The holdout section MUST show the guarded command's recorded results unedited when they
  exist (010), and "not run yet" otherwise.
- **FR-009**: Gemini's report code, its committed report with typed-in numbers and its figures MUST be
  replaced.
- **FR-010**: Unit tests MUST run the command on synthetic recorded runs (a temporary MLflow store):
  the report's numbers equal the recorded ones; a missing question stops it; trial runs are ignored;
  two runs give identical files.
- **FR-011**: How to regenerate the report from a fresh clone plus the data MUST be written down (the
  notebooks first, then the command).

### Key Entities

- **Recorded run set**: one question's runs from one execution of its approved notebook, with its
  commit, export date and data hash.
- **Report tables**: the tables a notebook records for the report (FR-002).
- **Model report**: the generated Markdown with its figures.
- **Model card data**: the generated data file the app reads.
- **Holdout record**: the guarded command's results per question (written by 010).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every number in the report and the model card data equals the corresponding recorded
  value (checked by the tests on synthetic runs, and on the real runs for one table per question).
- **SC-002**: Running the command twice on the same runs gives identical files.
- **SC-003**: The report covers the three questions, each with every level × every test year, the
  choice, the bands with hit rates, the hypotheses and the frozen model.
- **SC-004**: The command finishes in under a minute (it reads the store; it fits nothing).
- **SC-005**: No file with typed-in model numbers remains in `docs/` or the app's model card data.
- **SC-006**: The three notebooks, re-run to record their tables, give the same numbers as their
  approved runs.

## Assumptions

- The report is written to `docs/report/` (Markdown and PNG figures) and committed: it quotes
  aggregates only, which the rules allow; the model card data is written beside it as JSON.
- The MLflow store is `data/mlflow.db` (git-ignored); a fresh clone rebuilds it by running the three
  notebooks after the data is built.
- Showing the model card data on the app's page belongs to the app (011); the holdout runs are
  written by 010.
- Out of scope: the hand-in report itself (019), which draws on this report; the daily scores (009).
