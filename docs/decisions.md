# Decision log

Every significant choice, what else was considered, and why. v2 decisions are numbered V2-n. The
v1 log (D1–D64) is in `docs/initialplan.md` §12 at tag `v1-final`; the v1 decisions that still
apply are summarised at the end.

## v2 decisions

| # | Decision | Alternatives | Reasoning |
|---|---|---|---|
| V2-1 | **Rebuild the project from scratch as a market research platform** for any US-traded stock (researcher's decision, 29 Oct 2026): fundamentals, dilution risk, the expected results-day move, expected volatility and an insider tracker, updated daily | Keep extending v1 | v1's universe, tables and staging were shaped by the insider study, the root of most of its problems ([lessons-from-v1.md](lessons-from-v1.md)); the four questions are independent (D63) |
| V2-2 | **Fresh `main`** from one new commit; v1's history kept only behind the tags `v1-final`, `prereg-v1`, `prereg-risk-v1`–`v5` (annotated, with their creation dates; no GitHub Release was ever made for `prereg-v1`) | Wipe all history; build v2 on a branch | A clean start without destroying the timestamped proof that the registrations came before any result |
| V2-3 | **Keep `data/raw/`** and its manifest as the source layer; delete every derived database and export and rebuild them from raw | Re-download everything | Raw files are unchanged downloads; Tiingo cannot be downloaded after 26 November |
| V2-4 | **The insider study's hypothesis tests are dropped**: insider data is a tracker only; no return claims; the insider holdout is not run | Re-implement the study with its registration unchanged | The researcher's choice. v1 found no signal on development data (H1–H3 null, no model above the base rate); the platform's value is in risk and facts |
| V2-5 | **Deadlines kept**: product v1 on 17 November, report on 18 November; work in priority order, cut in a stated order ([plan.md](plan.md)) | Move the deadline | The capstone dates are fixed |
| V2-6 | **Six-layer design** ([architecture.md](architecture.md)): raw, complete per-source staging, reference and core with `known_at`, daily features, labels, models and scores, a read-only serving snapshot; one build database | v1's warehouse and panel databases | Each v1 problem traced to a missing layer: no security master, staging by project, batch-only, no serving copy |
| V2-7 | **Tiingo prices for every listed company**, fetched on 29 October while the plan is active, as a complete second source (cross-check, gap-fill) | Fetch only the ~200 gaps | A complete second source is only obtainable before 26 November; about one hour of downloads |
| V2-8 | **`config/risk_params.yaml` v5 is carried over unchanged**, so the risk registration (`prereg-risk-v5`) and its sealed holdout still hold | Rewrite the risk definitions | The definitions were checked on real data in v1; changing them now would be after seeing development results |
| V2-9 | **The 50% fall forecast is dropped** (researcher, 29 Oct); its label definition stays in `risk_params.yaml` v5, unused | Keep it as a rank against other stocks | Its ranking worked but its level could not be forecast (it follows whether a crash comes); v2 keeps three forecasts |
| V2-10 | **The volatility range's multiplier is set on all earlier years' calibration data**, not the last six months (researcher, 29 Oct; decided before the risk holdout test, which tests it) | v1's six-month scaling | v1's 80% range covered 74–76% of moves after 2019 because six months is one market mood; the exploratory pooled check gave 78–84% |
| V2-11 | **A price-only coverage level** (researcher, 29 Oct): stocks traded in the US that file nothing periodic with the SEC (about 960, e.g. Hitachi, Deutsche Telekom) get prices and the volatility forecast | Cover SEC filers only | Volatility needs only prices; a tool for any stock should not drop large foreign companies |
| V2-12 | **v1's GitHub issues are closed** with a pointer to `v1-final`; one issue per v2 plan step is opened (researcher, 29 Oct) | Keep tracking v1's issues | The board should show v2's work |
| V2-13 | **Features are computed as of any trading day, for three sets of rows**: month-ends (the volatility and dilution training panel), the close before each results release (the results-move training rows; v1 used the latest month-end) and each company's latest day (the product). Four definition changes from v1: values count from their `known_at` (v1: the filing date); a share count is put in the row date's shares with the split factors (v1 ignored a split after the count, so market value was off until the next report); short-selling ratios use trailing windows (v1's calendar months look ahead from a mid-month row); `months_since_report` counts 20-F and 40-F reports too | A full daily feature table (about 40 million rows); v1's month-end panel only | The same definitions serve training and the product at a fraction of the size; each change removes a look-ahead or an error, and all come before any v2 label or model result |
| V2-14 | **The insider tracker covers sales as well as purchases**: `core.insider_activity` has one row per filing and side, with the entity, its role, plan and offering flags and holdings; the tracker's rules (v1's gates, roles, clusters and 91-day cooldown) move to `config/tracker.yaml`, outside the registration | Purchases only, as in v1's study | The spec promises buys and sells; with the study dropped (V2-4) these rules decide what the tracker shows, not a test |
| V2-15 | **Financial values with impossible dates are left out of `core.financial_fact`** (1,163 of 16.1 million: a period ending more than 31 days after the filing that reports it, or before 1950, such as 2201 typed for 2015); staging keeps them as reported | Keep them; repair the year | They broke the date arithmetic, and guessing the intended year is not safe |
| V2-16 | **Daily SEC data comes through the nightly master index of each filing day**: per day, the headers of the filings whose details are used, the financial values of that day's periodic filers and the history of new registrants; **Form 3, 4 and 5 filings are fetched as full submissions and parsed into the quarterly data sets' tables**, a data set's version winning once published, with a table of differences (feature 001, research R2–R5) | Download the bulk `submissions` and `companyfacts` copies every day (about 3 GB a day); wait for the quarterly Form 4 data sets (up to three months late); the "latest filings" feed | About 600 small requests a day, a complete list per day, and insider trades in the tracker the evening after they are filed; the parser is checked against a past quarter's data set |
| V2-17 | **Prices update through a short daily window for every listed symbol** (Yahoo: batches of 200, the last 10 days; Tiingo: new days per ticker while the plan lasts), **with a full history refetched when a window shows a split or dividend**; per ticker the newest full history plus later windows make the series | Refetch every full history daily; append windows forever without refetching | Adjusted closes change for the whole past after a split or dividend; a window alone would leave the old adjustment |
| V2-18 | **A listed company's own ticker (in the SEC's latest list) is accepted from either price source on dates alone**, and its history starts at the ticker's current listing (the later of the listing start and the day after another company last used the symbol) | v1's name and exchange identity checks for every ticker | The SEC list is the identity; renamed companies and foreign ADRs failed the name check and went unpriced (78 Tiingo-only, most of 956 price-only stocks) |
| V2-19 | **The daily update re-stages only sources with new files and rebuilds every layer above staging in full**, recorded in `ops` and checked by `sentinel verify` (a full rebuild compared table by table) and the truncation test | Incremental inserts per layer | Full rebuilds of the upper layers take minutes and cannot drift from a rebuild; incremental code would need its own proof of equality |
| V2-20 | **The schedule is a Windows Task Scheduler task** (weekdays 23:00, run after a missed start, one at a time) that starts WSL and runs `sentinel update --scheduled`, which puts itself under the 5 GB memory cap | A systemd timer or cron inside WSL | WSL is usually shut down when no terminal is open, so a timer inside it would not fire; the update catches up missed days itself |
